## What runs where

Dawn implements a host API for creating resources, compiling shaders, recording commands and submitting device work. Its native frontend owns WebGPU validation/state; native backends translate that work to graphics APIs. Wire is a separate client/server API transport. Tint is a host-side shader compiler used by Dawn and standalone tools. Generated headers and proc tables connect these layers; generating a shader or recording a dispatch is not GPU execution.

The source path reviewed here is: API call → frontend validation/encoding → queue submission → selected backend/native API. Shader text travels through Tint reader/resolver/IR/writer stages. Buffer mapping and completion callbacks provide host-visible boundaries; they are not interchangeable with a submitted-command return. The [lifecycle guide](dawn/resource-lifecycle.md) traces the actual implementations.

## Build-system identity is not package identity

- [CMake](https://github.com/hsoliwal/dawn/blob/1ab42ee97300054135e1ec57ac81eedf21da6358/CMakeLists.txt) declares the Dawn project and includes Tint/native/wire/support targets according to options
- [Bazel module declaration](https://github.com/hsoliwal/dawn/blob/1ab42ee97300054135e1ec57ac81eedf21da6358/MODULE.bazel), [Bazel workspace](https://github.com/hsoliwal/dawn/blob/1ab42ee97300054135e1ec57ac81eedf21da6358/WORKSPACE.bazel) and [GN root](https://github.com/hsoliwal/dawn/blob/1ab42ee97300054135e1ec57ac81eedf21da6358/BUILD.gn) are additional build entry points; the current pass inventories their files but does not assert target parity across build systems
- Tint's `BUILD.cmake` files are generated. Their own headers point to `tools/src/cmd/gen` and the generation template. They were read, not modified or regenerated
- C++ namespaces, C++ modules, CMake targets, GN targets, Bazel packages and Go packages are different entities. Directory counts below must not be reported as a complete C++ namespace count
- The tree records 67 Git submodule entries. Their pinned references are listed in the inventory; their external contents are not expanded into this repository's source audit

## Configuration, errors and ownership

Use [building](building.md) and [CMake quickstart](quickstart-cmake.md) for dependency/setup commands. Backend and Tint reader/writer build switches determine compiled capabilities. A compiled backend still needs the appropriate native runtime/device and requested feature/limit support. The [support guide](support.md) describes upstream platform context; it is not a qualification of this fork's commit.

Object validation, asynchronous results, device loss and native errors have different reporting paths. Read [Dawn errors](dawn/errors.md) and [device facilities](dawn/device_facilities.md), then the selected implementation. Do not assume all failures throw C++ exceptions or all asynchronous callbacks run inline. Resource mappings, pending serials, wire handles and backend allocations have distinct owners.
